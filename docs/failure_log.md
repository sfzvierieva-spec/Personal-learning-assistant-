## 1. Questionnaire pivot: questions that changed nothing in the output

**What happened.** The first questionnaire mixed useful questions with
"meta" questions about study habits: chronotype (morning or evening), spacing
habits, attack angle, session length. The answers were stored, but they did
not visibly change the study material that was generated.

**Why it was a problem.** The point of the project is that personalization
is *visible*: two learners should get two different outputs. A question that
changes nothing makes the user work for nothing and weakens the demo.

**Fix.** Questionnaire v2 replaced these questions with 8 questions that
each drive one concrete output decision: main format, density, explanation
style, what usually loses the learner, study goal, reading vs testing
balance, tone and visual layout. Schema, prompt generator and tests were
updated, and `QUESTIONNAIRE_VERSION` was bumped to 2.0.

**Evidence.** Commit `2e26f85` "Refocus questionnaire on direct
output-shaping decisions (v2)"; `profile_and_prompts/profile/schema.py`.

**Lesson.** Every question must map to something you can see in the output.
If you cannot say what a question changes, remove it.

**Leftover.** The prompt files `profile_and_prompts/prompts/v1`–`v4` still
describe a learner from the first questionnaire (25-minute sessions, studies
in the morning).

## 2. Profile summary too clinical

**What happened.** The first version of the profile summary shown to the
user mirrored their answers back almost word for word ("based on your
answers, you prefer X, Y, Z"). It read like a receipt.

**Why it was a problem.** The user should feel understood. But the obvious
way to sound warmer, compliments, is exactly the sycophancy failure mode we
must avoid.

**Fix.** `summarize_profile()` was rewritten to *interpret* rather than
mirror. It now writes two observation sentences that combine several
answers, then bullets showing how each answer shapes the material. It is
written in the second person ("you") and still makes no judgment about the
learner's character. It is template-based, not generated by the LLM, so it
cannot drift into flattery.

**Evidence.** Commit `2e26f85` (same commit as the questionnaire v2);
`profile_and_prompts/profile/builder.py`.

**Lesson.** Interpreting without flattering is possible: describe what the
answers imply for the material, never what they say about the person.

## 3. Mock drift between the profile module and the interface stub

**What happened.** To work in parallel, the interface used a stub (a fake
copy) of the profile module (`interface/tests/fixtures/live_stub/`). The
stub followed an early version of the contract, but the real module changed:

| | Stub (old contract) | Real module |
|---|---|---|
| Question text key | `text` | `question` (+ `axis`, `multi_select`) |
| Options | list of strings | list of `{label, value}` dicts |
| `build_profile()` returns | a dict | a pydantic `Profile` object |

**Why it was a problem.** The interface tests passed against the stub, but
the UI would have crashed as soon as it was connected to the real module.

**Fix.** PR #8 (Léna, "Fix stub drift so interface integrates with the real
profile_and_prompts"):
- the interface now reads `question` and `{label, value}` options;
- the stub mirrors the real shape;
- `interface/requirements.txt` adds `pydantic` and `jinja2` so the real
  module can be imported.

**Evidence.** PR #8, commit `96b164c`.

**Lesson.** A stub is a copy of a contract and goes stale silently. When a
module's interface changes, update the stubs in the same PR, or test against
the real module.

## 4. v4 adds facts that are not in the course in its "why" lines

**What happened.** David ran prompt v1 and v4 on the same course (PR #7).
v4 asks the model to add brief "why it works" explanations. In
`outputs/v1_vs_v4/flashcards_v4.json` one card says:

> "A matrix M in M_n(R) is not invertible if and only if 0 is an eigenvalue
> of M. Why: having 0 as an eigenvalue implies a non-trivial kernel."

The maths is correct, but the course never mentions a kernel there: the
model added it from its own knowledge.

**Why it is a problem.** It is a hallucination in the strict sense of the
project: content that is not in the learner's course. Two instructions in v4
conflict, "explain why" and "use only the source", and here the first one
won.

**Status.** Open, target of prompt v5. Proposed fix: "explain why **using
only what the course says**; if the course does not say why, skip the why."

**Evidence.** `outputs/v1_vs_v4/README.md` (observation 2) and
`flashcards_v4.json`; analysis in `evaluation_db/PROMPT_EVALUATION.md`.

**Lesson.** Adding an instruction can create a new failure mode. Each new
rule must be checked against the guardrails it could conflict with.

## 5. Chaotic Git workflow at the start

**What happened.**
- Files were added with GitHub's "Upload files" button instead of
  `git add` / `commit` / `push` (commits named "Add files via upload").
- `create_database.py` was pushed onto Léna's branch
  (`lena/profile-and-prompts`) instead of Hugo's, reached `main` through her
  PR #3, and sat at the repo root instead of the agreed `evaluation_db/`
  folder.

**Why it was a problem.** The Git workflow counts for 25 % of the grade.
Uploads do not show a real local workflow, and pushing to a teammate's
branch mixes two people's work in one PR.

**Fix.**
- From then on, all work was done locally with `git add` / `commit` /
  `push`.
- The database work was moved with `git mv` to `evaluation_db/` on Hugo's
  own branch and merged through PR #6, reviewed by another pole.
- Team rules:
  - one branch per person, never push to a teammate's branch;
  - never use the upload button;
  - every PR is reviewed by someone from another pole.

**Evidence.** Commits "Add files via upload" (`0191eb3` on
`lena/profile-and-prompts`, `eb07624` on `hugo/documentation-and-database`);
PR #6 (commit `16053b8`, "Move create_database.py into evaluation_db/").

**Lesson.** Agree on the workflow on day one: branch per person, local
commits, PR with a cross-pole review, merge.
